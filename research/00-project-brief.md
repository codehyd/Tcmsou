# 中医管理项目：需求原始记录与研究范围

记录日期：2026-11-13。项目名称：中医管理项目；仓库：https://github.com/codehyd/Tcmsou 。

## 用户提出的方向

1. 收集和保存黄芪、陈皮等中药材，逐步扩大材料目录；“所有中药”是长期愿景，本轮需要研究目录边界、来源和维护成本。
2. 从二维药柜逐步转向三维收藏空间。体验参考《三角洲行动》的收藏室及特勤处，借鉴陈列、空间导航和沉浸感，不直接复用该游戏的模型、界面或美术资产。
3. 在三维场景中选取自己的药材并进行制作/烹饪演练。锅是一种器具，还需研究其他制作方式。演示动画、制作流程和真实药理效果必须分别描述，不能把视觉效果当药效验证。
4. 编写和管理中药处方单；考虑用 Leafer 自定义编辑模板，并进行字段与数据映射。现有处方编辑功能和未来 Leafer 模板功能必须分别核实。
5. 后续考虑 Minecraft 服务器：用户能实际进入游戏，通过种子、地图、模组或插件呈现中药主题场景。它是候选路线，尚未决定替代网页三维方案。

## 当前主要阻塞

用户尝试生成药材三维模型，但感觉“太塑料”，因此暂停该方向。研究应先区分几何形态、表面纹理、PBR 材质、光照、比例与镜头导致的问题，再评价资产获取路线；不能直接承诺 AI 一键生成可信药材模型，也不能未经比较就决定转做 Minecraft。

## 第一阶段：市场与可行性研究

本阶段只做公开资料检索、现有实现的只读核对、研究文档及 Multica 任务协作。禁止修改业务源码、运行仓库内脚本、安装依赖、训练/购买模型、购买服务、部署、开服、合并主干或代用户联系受访者。报告可以新增在 research/；不覆盖已有文件。必要的技术实验先提出有边界的计划，等待本阶段研究评审后决定。

初始受众作为假设研究：中医学习者、药材爱好者、收藏/科普用户、教育机构；不要未经验证直接把它定义为临床诊疗或药房经营系统。处方模块先研究记录、模板和学习用途，不擅自增加自动诊断、推荐用药、剂量计算或疗效承诺。

## 研究交付与验收

- 市场：至少 6 个真实可访问的直接/间接替代产品，覆盖药材资料/识别、收藏管理、处方记录/模板、三维科普或游戏化学习；说明用户、核心功能、价格证据、更新状态和替代关系，不凑数量或虚构用户访谈。
- 用户：分开记录用户原始需求、公开用户证据、研究假设与待验证问题；提出可执行的访谈提纲/低成本验证计划，不能把拟议访谈当已完成。
- 资产：对陈皮、黄芪、菊花等不同形态建立样例标准，比较实拍图/2.5D、摄影测量、人工建模/PBR、AI 生成后人工处理和风格化低多边形；列明版权、预算、人工时间、设备与网页性能边界。未实测的质量和成本明确标注估算。
- 技术：核对已有 React 药柜、处方模块、陈皮 GLB/Blender 资产与 Three.js 实验原型；比较独立网页、混合 2D/3D、Minecraft 的适用场景、联动方式与维护成本。种子不等于定制中药玩法。
- 模板：研究 Leafer 编辑、字段映射、导入导出/打印、持久化和数据模型要求，区分已有功能与计划。
- 质量：每个关键结论给可核验 URL、来源日期/访问日期及局限；对核心来源逐项独立复核。第三方药材图片、数据库和模型的可访问性不等于允许复制、修改、训练或商用。
- 决策：输出一个可验证的最小版本建议、备选路线、延期清单、风险和粗略成本假设；明确推荐 go/pivot/no-go 及所需用户决定，研究通过不等于授权开发。

## 协作和成本

项目经理协调；产品经理负责市场和需求、UI/UX 负责场景与交互研究、技术负责人负责资产与技术路线、测试工程师独立核查证据。前后端及运维本阶段不接业务开发。沿用现有 Cursor 默认模型与单任务并发；未经另行明确调整，不自动升档、切 Fast 或使用 Other Models。避免无新证据的重复催办、重复委派和循环评审。

研究产出须在本项目任务中保留版本和链接。本地运行环境必须实际在线；没有 active run 或有效交接触发时，不声称项目会持续自动推进。
